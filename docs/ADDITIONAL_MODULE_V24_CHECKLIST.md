## 2. Decisions

| # | Decision | Reason |
|---|---|---|
| D1 | Only the name of a built-in type changes; its base type, "active" and the rule that it is not deleted stay. | The modules go by what an account is (Bank is offered where money is paid or received, Accounts Receivable holds the invoices); renaming must not change what the program does with the accounts. |
| D2 | The original name stays the built-in type's own: no other type takes it, and a file to import that says it still means the type. | Files kept from before, templates and other systems say Bank, Fixed Asset, Income; they must keep reading the same way after a type is renamed. |
| D3 | A renamed built-in type alone in its group of the statements heads the group (Property and Equipment in place of Fixed Assets); with other types in the group it has its own heading and total. | The name the cooperative chose is then on its statements once, without a group and a type of the same meaning one under the other; a group of several types (Current Assets) keeps its own name. The totals do not change. |
| D4 | Where the program shows what an account behaves as (Chart of Accounts, the picker, the budgets, the messages) it uses the built-in type's new name; on the built-in type's own page Behaves as shows its original name. | One name for one type everywhere; the page of the type itself says which built-in type it is. |
