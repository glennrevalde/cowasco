# Additional module for the Water + Coop systems (v4): requirements checklist

This maps every request of the workbook `ADDITIONAL_MODULE_FOR_WATER_COOP_SYSTEMS_v4.xlsx` to the code that implements
it and the test that exercised it. **Sheet2** repeats the requests of the v3 workbook, all done in version 31
(`docs/ADDITIONAL_MODULE_V3_CHECKLIST.md`); they were checked again with the tests below. **Sheet3** holds the new
requests: eight screenshots with notes (rows 2 to 198). Status: **Done** means built, reachable from the menu, and run
in the tests or by hand on the sample database.

The database change is one upgrade script, `database/migrations/2027_01_03_loan_collection_error_correct.sql`
(MySQL 5.5, safe to run twice). New installations get the same through `database/schema.sql` and `tools/install.php`.

## 2. Decisions

| # | Decision | Reason |
|---|---|---|
| D1 | An error correction of a loan payment is a line of its own on the loan ledger (kind Correction, the amounts negative, linked to the payment), the payment stays marked corrected; the receipt's journal entry is reversed line for line: a cash voucher of the teller's drawer for a cash payment, a journal voucher for a check or bank payment (the cheques no longer wait on Check Clearing). The schedule, the balances, the status and the last payment date are worked out again; a payoff corrected opens the loan again with the holds on the deposits. | The passbook keeps both lines (EC printed negative), as for savings (version 31); the books show the reversal on the day it is made. |
| D2 | Error Correct is refused for a receipt that also holds other items, a cheque already cleared to the bank, and a payment from savings; the message says how to correct those (void the receipt, a returned check, a loan adjustment). Correcting another teller's payment, or one of an earlier day, needs a supervisor. | A partial reversal of a receipt, or of money already in the bank, would leave the receipt or the bank reconciliation wrong. |
| D3 | Delete is a void with the reason, refused once the collection is printed in the passbook or corrected; the teller's own collection of the day at once, anything else with a supervisor. | The same rule as Savings Account Transaction. |
| D4 | Payment Mode offers Cash, Check and Bank. A member who has resigned, been terminated or died can still have a loan paid from the deposits (a fourth mode shown for such a member only, with a supervisor's approval). | The workbook's three modes; the settlement of a member who has left keeps working. |
| D5 | "Excess to savings" and "Cash received / Change" of the previous loan page are not on the form; a payment above what the loan can take is refused with the payoff in the message. "Pay off" stays as **Full payment**. | The former form has neither; a payoff of a diminishing-balance loan includes the interest to date, which the amount alone does not carry. |
| D6 | #of Amort. is a row of the grid under Amortization Due (for each of the three columns) rather than a box beside it. | The same figures, readable on a phone where the boxes stack. |
| D7 | The class of the entry is chosen at the bottom of the list, in the place of Branch, Division and Segment; the branch of the receipt stays the member's branch. | The Class List is the system's dimension for branches, divisions and segments, required on every cooperative entry. |
| D8 | The printed sheets (validation, passbook lines, reprint, footer, cover) set no page margin, so the browser prints no title, address or page number; the positions are those of the passbook type and the slip margins. | What the workbook asked to erase is what the browser prints in the page margins. |

## 3. Upgrade

Back up the database, copy the files over the installation and run
`database/migrations/2027_01_03_loan_collection_error_correct.sql` (phpMyAdmin Import, Navicat Execute SQL File, or
`php tools/upgrade.php`). Then follow `UPGRADE_v32.txt`: the slip margins on Passbook Types and the browser's print
settings.
