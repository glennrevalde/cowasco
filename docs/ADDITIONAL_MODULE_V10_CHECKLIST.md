## 2. Decisions

| # | Decision | Reason |
|---|---|---|
| D1 | One review page for every import (members, savings, time deposits, batch deposit and withdrawal, items): the rows travel back as one JSON field, and every check runs again on upload. | The same way of correcting and removing rows everywhere; a file of thousands of rows is never cut short by the server's limit on form fields; nothing the browser sends is trusted. |
| D2 | The upload is all or none, in one database transaction. | A migration file half loaded is harder to correct than one refused with its rows marked. |
| D3 | The imported balances are entered with a savings transaction code whose GL account takes the other side; the migration adds INI against Opening Balance Equity. | The workbook asks the user to choose the code for the journal entry; Opening Balance Equity is where opening balances go (the Opening Balances Import of Members & Others does the same). |
| D4 | One voucher per cut-off date and code (savings) or per code (time deposits), not one per account. | The general ledger gets one readable entry per migration batch; each account still gets its own ledger line. |
| D5 | Import Member is for individual members. | The workbook lists the required fields of individual members; joint and institutional members are added on Member Information. |
| D6 | A batch withdrawal is checked with the very rules of the posting (`Savings::checkMove`), on the balance left by the rows above it. | The review then says which row would fail, instead of the whole batch being refused at the end. |
| D7 | A hold cannot be larger than what is withdrawable. | Otherwise a hold could make the available balance negative. |
| D8 | The receipt accounts also leave out share capital and the inventory accounts of the items. | Share capital is kept by the savings ledger, and an inventory account by the item ledger; money for them is received on their own pages, so the books and the ledgers keep agreeing. |
| D9 | Member Disbursement and Cooperative Vouchers leave the menu but their pages stay. | Vouchers already made must still open, print and be voided; a member who has left is still settled, and unclaimed distributions are still paid. |
| D10 | The item import of System Administration (Import from CSV) stays; Import items uses the same functions. | One set of rules for an item, whichever page the file comes through. |
| D11 | Every upload of a review is sent once (a single-use token, as on the teller's forms). | A refresh, Back or a second tab must never post a batch or place time deposits twice. |
| D12 | The review applies the rules the posting applies: the closing date for the savings cut-off date, the back-dating policy for the time deposit posting date and the batch date, the member's status (a time deposit for an active member only), the product's maximum balance, the rules of a withdrawal on the balance left by the rows above. A member no. drawn for a row without one skips the numbers already used, those of the file included. | A row marked ready is then posted as shown; nothing fails at Upload without its row being named. |
| D13 | The member name must hold every word of the last name and the first name on file (a first name may be shortened, "Ma." for Maria). | A wrong member code for someone with the same surname is caught before the balance goes to the wrong member. |
| D14 | Import items asks for the rights of what it does: Create on the Item List, Edit for an item already on it, Create on Adjust Quantity/Value on Hand for an opening quantity. | The same rights as entering the items and their opening stock by hand. |
| D15 | Cooperative Vouchers and Member Disbursement are taken out of the menu, not deleted. | Their vouchers are in the books; deleting the pages would leave them without a page to open, print or void them. |
